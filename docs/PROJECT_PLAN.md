# Chessy — план проекта

Статус документа: основной архитектурный план
Последнее обновление: 2026-08-06

## 1. Идея проекта

Chessy — персональный шахматный бот, который должен пройти три стадии развития:

1. Самостоятельно приобрести базовое шахматное понимание через self-play RL.
2. Перенять стиль владельца из исторических и новых партий.
3. Продолжить усиливаться через RL, не потеряв персональные особенности игры.

Проект одновременно является шахматным продуктом и исследовательской
лабораторией. Важен не только итоговый уровень игры, но и наблюдаемая эволюция:
от случайной policy до базового агента, персонализированного Chessy и его
последующих поколений.

## 2. Основные принципы

- Правила шахмат задаются средой, а не изучаются нейросетью.
- Нелегальные ходы всегда маскируются до выбора действия.
- Базовое шахматное понимание сначала приобретается через RL-curriculum.
- Персонализация выполняется поверх универсального RL-чекпоинта.
- После персонализации self-play продолжается совместно со стилевым loss.
- Любой значимый чекпоинт должен быть доступен для игры через интерфейс.
- Обучение должно безопасно останавливаться и продолжаться с полного snapshot.
- Все улучшения силы и сходства со стилем подтверждаются измерениями.
- Тестовый набор остаётся неизменным и не участвует в выборе конфигурации.
- Исходные партии и human-feedback хранятся неизменяемыми; производные
  датасеты всегда можно пересобрать.

## 3. Доступные вычислительные ресурсы

Основная машина:

- MacBook Pro;
- Apple M3 Pro;
- 12 CPU-ядер: 6 производительных и 6 эффективных;
- встроенный 18-ядерный GPU;
- 36 ГБ объединённой памяти;
- macOS.

Основная цель — сделать весь цикл разработки и небольшие RL-запуски возможными
локально. Архитектура не должна требовать CUDA. Первичная реализация обучения
планируется на PyTorch MPS; MLX остаётся вариантом оптимизации под Apple Silicon.

## 5. Общая архитектура системы

```text
Шахматная среда
      ↓
Policy/value network ←→ MCTS
      ↓                 ↓
Self-play actors     Игровой API
      ↓                 ↓
Replay buffer       Локальный UI
      ↓                 ↓
RL trainer          Human-feedback
      ↓                 ↓
Training snapshots ← Персональный датасет
      ↓
Playable exports
```

Система разделяется на компоненты с устойчивыми интерфейсами:

- chess environment;
- кодирование позиции и действия;
- policy/value model;
- MCTS;
- self-play workers;
- replay buffer;
- trainer;
- evaluation arena;
- игровой API;
- локальный web-интерфейс;
- human-feedback pipeline;
- snapshot/export manager.

## 6. Шахматная среда

Среда отвечает за:

- генерацию легальных ходов;
- шах, мат и пат;
- рокировку;
- взятие на проходе;
- превращение пешки;
- недостаточный материал;
- троекратное повторение;
- правило 50 ходов;
- сериализацию FEN, UCI и PGN;
- terminal reward: победа `+1`, ничья `0`, поражение `-1`.

На раннем этапе допустимо использовать `python-chess` как проверенную реализацию
правил. Корректность дополнительно проверяется perft-тестами на известных
позициях.

Нейросеть не должна тратить capacity на изучение легальности. Нелегальные
действия получают `-inf` до softmax.

## 7. Представление позиции и действия

### 7.1. Вход сети

Планируемое представление:

- текущая позиция и семь предыдущих позиций;
- 12 плоскостей фигур на каждую позицию;
- сторона хода;
- четыре права рокировки;
- поле взятия на проходе;
- информация о повторениях.

Ориентировочно получится 100–105 плоскостей размером `8 × 8`.

Доска остаётся в фиксированной ориентации: белые всегда находятся с одной
стороны. Это позволяет сохранить различия личного репертуара белыми и чёрными.

Перед началом supervised-обучения текущий датасет нужно дополнить историей
последних позиций и результатом партии относительно стороны хода.

### 7.2. Пространство действий

Используется AlphaZero-подобное кодирование:

```text
8 × 8 × 73 = 4672 действия
```

Оно покрывает линейные ходы, ходы коня и варианты превращения пешки. Кодирование
должно быть единым для supervised policy, MCTS, self-play и игрового API.

## 8. Нейросеть

Базовая конфигурация v0.1:

| Параметр | Значение |
|---|---:|
| Архитектура | Residual CNN |
| Residual-блоки | 8 |
| Каналы | 96 |
| Нормализация | GroupNorm |
| Активация | ReLU |
| Ориентировочный размер | 1–2 млн параметров |
| Policy head | 4672 действия |
| Value head | Win/Draw/Loss |

Модель должна быть небольшой ради локального self-play и массового MCTS
inference. Transformer не является первой реализацией: он дороже и менее удобен
для начального RL-цикла на доступном железе.

Value head выдаёт три вероятности вместо одного скаляра. Для MCTS их можно
преобразовывать в ожидаемое значение позиции.

## 9. MCTS

MCTS использует:

- policy сети как prior;
- value сети вместо случайных rollout;
- PUCT для выбора ветвей;
- Dirichlet noise в корне при self-play;
- temperature для разнообразия первых ходов;
- пакетную оценку листьев на GPU;
- transposition-aware оптимизации только после корректной базовой версии.

Число симуляций должно быть конфигурируемым отдельно для:

- раннего curriculum;
- основного self-play;
- evaluation arena;
- игры с человеком.

Предварительный диапазон для локального старта — 64–200 симуляций на ход.
Конкретное значение выбирается после бенчмарка throughput и силы.

## 10. RL-curriculum

Полный AlphaZero с начальной позиции слишком дорог для случайной сети на одном
Mac. Поэтому обучение остаётся чистым self-play RL по награде за исход партии,
но распределение начальных позиций усложняется постепенно.

### Стадия A. Простые окончания

- король и ферзь против короля;
- король и ладья против короля;
- простые пешечные окончания;
- небольшое количество фигур.

Цель — научить terminal value, матование и базовую координацию.

### Стадия B. Уменьшенный материал

- легальные позиции с 6–16 фигурами;
- примерно сбалансированные позиции;
- тактика, защита короля, превращение преимущества.

### Стадия C. Полные шахматы

- стандартная начальная позиция;
- легальные дебютные позиции;
- self-play против текущей и исторических версий.

Curriculum не должен добавлять искусственную награду за материал. Основная
награда остаётся результатом партии, чтобы агент не научился выигрывать фигуры
вместо выигрывания шахмат.

## 11. Условия получения базового RL-чекпоинта

Переход к персонализации определяется не временем обучения, а измеримыми
критериями:

- агент стабильно реализует базовые маты;
- уверенно побеждает случайного легального агента;
- превосходит простой material-based alpha-beta baseline;
- новые поколения обыгрывают исторические версии;
- value различает выигранные, ничейные и проигранные позиции;
- policy больше не близка к равномерному распределению.

Зафиксированная универсальная версия получает имя `base_rl`.

## 12. Персонализация

Персонализация начинается с `base_rl`, а не со случайных весов.

Supervised loss:

```text
L = L_policy + 0.25 × L_value
```

Предварительные веса источников:

| Источник | Вес |
|---|---:|
| Хороший ход из слабой исторической партии | 0.75 |
| Ход из полной исторической партии ≥82% | 1.0 |
| Сохранённый ход из живой игры против Chessy | 4.0 |

Ходы из полных партий не штрафуются дополнительно за индивидуальную accuracy:
они сохранены целиком именно ради характера и последовательности решений.

Из одной исторической партии на эпохе выбирается не более 16 случайных позиций,
чтобы длинные партии и повторяющиеся дебюты не доминировали.

Предварительная конфигурация supervised-этапа:

| Параметр | Значение |
|---|---:|
| Backend | PyTorch MPS |
| Precision | float32, затем benchmark mixed precision |
| Batch size | 512 |
| Optimizer | AdamW |
| Learning rate | `3e-4`, для fine-tuning возможно `1e-4` |
| Weight decay | `1e-4` |
| Scheduler | cosine decay |
| Warmup | 5% шагов |
| Максимум эпох | 30 |
| Early stopping | 5 эпох |
| Gradient clipping | `1.0` |

## 13. RL после персонализации

Чистый self-play способен стереть личный стиль. Финальная стадия использует
смешанную цель:

```text
L_total = L_RL + λ_history × L_personal + λ_live × L_human_feedback
```

Должны существовать конфигурируемые режимы игры:

- `strength` — преимущественно RL policy;
- `balanced` — сила со стилевым prior;
- `personal` — усиленное влияние персональной policy;
- регулируемый `style_strength` от 0 до 1.

При необходимости personal policy может быть отдельным замороженным prior,
который смешивается с RL-policy перед MCTS. Это надёжнее полного доверия одной
сети, склонной забывать старые цели.

## 14. Интерфейс игры против чекпоинта

Нужен локальный web-интерфейс, доступный на Mac без внешнего сервера.

Функции стартового экрана:

- выбор чекпоинта;
- выбор цвета или случайный цвет;
- контроль времени;
- число MCTS simulations или понятный уровень силы;
- настройка температуры и разнообразия;
- переключатель «Добавить мои ходы в обучение»;
- переключатель по умолчанию выключен.

Во время партии:

- легальная интерактивная доска;
- часы;
- история ходов;
- индикация размышления бота;
- сдача, предложение ничьей и перезапуск;
- корректная обработка превращения пешки.

После партии:

- результат и PGN;
- checkpoint ID и параметры MCTS;
- скачивание PGN независимо от обучения;
- финальное подтверждение добавления в human-feedback.

Первый осмысленный RL-чекпоинт должен быть playable. Интерфейс не откладывается
до окончания всего обучения.

## 15. Human-feedback

Если пользователь подтверждает сохранение, записываются:

- исходный PGN;
- дата и контроль времени;
- цвет пользователя;
- результат;
- checkpoint ID и хеш весов;
- параметры MCTS;
- позиции перед ходами пользователя;
- ходы пользователя;
- версия формата.

Ходы бота сохраняются как контекст, но не используются как человеческие
policy-targets. В целевые примеры попадают только ходы пользователя.

Предлагаемая конфигурация:

```yaml
play:
  save_for_training_default: false
  require_post_game_confirmation: true
  allow_pgn_download: true

human_feedback:
  enabled: true
  sample_weight: 4.0
  max_batch_fraction: 0.25
  include_human_moves: true
  include_bot_moves_as_targets: false
  preserve_raw_pgn: true
```

Высокий вес не означает физического копирования строки четыре раза. Он
применяется к loss. Доля human-feedback ограничивается 20–25% batch, чтобы одна
партия не вызвала мгновенное переобучение.

Новые human-feedback-партии никогда не добавляются в замороженный исторический
test. Они формируют отдельный поток для следующего training snapshot.

## 16. Возобновляемое обучение

Различаются два типа артефактов:

- playable model export — веса для MCTS и интерфейса;
- full training snapshot — полный слепок для продолжения run.

Training snapshot включает:

- веса модели;
- optimizer state;
- scheduler state;
- epoch и global step;
- random state Python, NumPy и PyTorch;
- состояние sampler;
- training config;
- dataset manifest;
- replay-buffer manifest;
- curriculum state;
- self-play league;
- метрики;
- версию кода и форматов.

Корректная остановка:

1. Перестаёт запускать новые self-play-партии.
2. Завершает или сериализует текущие партии.
3. Сбрасывает очереди результатов.
4. Фиксирует replay buffer.
5. Завершает текущий batch.
6. Атомарно создаёт snapshot.
7. Завершает процесс.

Поддерживаются режимы:

- `resume` — продолжение того же run с неизменной критической конфигурацией;
- `fork` — новый эксперимент из snapshot с изменёнными параметрами.

Запись snapshot выполняется во временную директорию с последующим атомарным
переименованием. Хранятся как минимум два последних snapshot на случай
повреждения одного из них.

Абсолютная побитовая идентичность после resume не гарантируется при параллельном
self-play и GPU, но состояние обучения и его статистический процесс должны
восстанавливаться полностью.

## 17. Политика хранения

Для модели на 1–2 млн параметров ожидается:

- playable export: 4–8 МБ;
- полный trainer snapshot: примерно 15–35 МБ;
- несколько важных snapshot: 100–300 МБ.

Replay buffer хранится отдельно неизменяемыми сегментами. Snapshot содержит
ссылки на сегменты, а не копирует весь buffer.

Политика по умолчанию:

- два последних автоматических snapshot;
- один лучший snapshot;
- один snapshot на завершённую стадию curriculum;
- игровые экспорты важных поколений;
- лимит активного replay buffer: первоначально 2–5 ГБ;
- старые self-play-партии могут архивироваться со сжатием.

Целевой объём активного эксперимента — не более 5–10 ГБ.

## 18. Метрики и оценка

### 18.1. Сила игры

- результаты против случайного агента;
- результаты против material alpha-beta baseline;
- матчи нового поколения с предыдущими;
- матчи против фиксированных версий внешнего движка;
- Elo с доверительным интервалом;
- отдельная статистика по стадиям curriculum.

Новая версия не объявляется сильнее по нескольким партиям. Требуется достаточная
выборка или последовательный статистический тест.

### 18.2. Персональное сходство

На validation измеряются:

- top-1, top-3 и top-5 move accuracy;
- policy cross-entropy;
- вероятность, присвоенная фактическому ходу;
- результаты отдельно белыми и чёрными;
- результаты для `full_game`, `good_move` и `human_online`;
- дебют, миттельшпиль и эндшпиль;
- распределения дебютов и характерных решений.

Test используется один раз после выбора архитектуры и конфигурации.

### 18.3. Финальный баланс

Сравниваются как минимум:

- `base_rl`;
- `personal_supervised`;
- `personal_rl`;
- версии после отдельных волн human-feedback.

Цель — построить кривую «сила против персонального сходства», а не свести всё к
одной метрике.

## 20. Этапы реализации

### Этап 0. Каркас и воспроизводимость

- выбрать структуру Python-проекта;
- зафиксировать зависимости;
- добавить единый config loader;
- определить run ID, seed и manifests;
- настроить тесты и базовые команды.

Критерий готовности: чистое окружение запускает тесты и читает конфигурацию.

### Этап 1. Среда и кодирование

- обёртка над правилами;
- perft-тесты;
- кодирование входных плоскостей;
- кодирование 4672 действий;
- legal mask;
- round-trip UCI/action.

Критерий готовности: все легальные ходы кодируются и декодируются без потерь.

### Этап 2. Модель

- residual policy/value network;
- forward pass на CPU и MPS;
- сохранение и загрузка model export;
- проверка маски policy;
- micro-benchmark batch inference.

Критерий готовности: случайный чекпоинт воспроизводимо загружается и оценивает
пакет позиций.

### Этап 3. MCTS и playable agent

- корректный PUCT;
- batched leaf evaluation;
- temperature и root noise;
- выбор хода;
- игровой API;
- минимальный локальный UI.

Критерий готовности: пользователь может сыграть против случайного или тестового
чекпоинта, а партия завершается по правилам.

### Этап 4. Training snapshots и инфраструктура run

- full snapshot schema;
- atomic save;
- `resume` и `fork`;
- periodic, best и stage snapshots;
- metrics log;
- dataset/replay manifests;
- graceful stop.

Критерий готовности: остановленный тестовый run продолжает обучение без сброса
optimizer, scheduler и global step.

### Этап 5. Self-play и RL-curriculum

- self-play workers;
- replay buffer;
- trainer loop;
- простые окончания;
- уменьшенный материал;
- полные шахматы;
- evaluation arena и historical opponents.

Критерий готовности: измеримый прогресс относительно фиксированных baseline.

### Этап 6. Персонализация

- добавить историю позиций и value targets в датасет;
- weighted sampler;
- supervised fine-tuning от `base_rl`;
- validation metrics;
- playable export `personal_supervised`.

Критерий готовности: персональная версия лучше `base_rl` предсказывает будущие
ходы владельца на validation и остаётся способной играть полноценные партии.

### Этап 7. Human-feedback

- необязательная галочка сохранения;
- подтверждение после партии;
- raw PGN и metadata;
- преобразование в policy samples;
- высокий loss weight с ограничением batch fraction;
- versioned feedback snapshots.

Критерий готовности: сохранённая партия появляется в следующем training run, а
несохранённая не оставляет обучающих примеров.

### Этап 8. Персональный RL

- смешанный RL/style loss;
- style-strength control;
- матчи `base_rl` / `personal_supervised` / `personal_rl`;
- анализ забывания стиля;
- настройка replay mix.

Реализован отдельный `personal-rl` run с фиксированным incumbent, раздельными
RL/historical/feedback потоками, snapshots и двойным promotion gate. Критерий
фактического завершения эксперимента остаётся строгим: Chessy должен усилиться
относительно персонализированного предка в достаточном paired arena, не теряя
установленный уровень сходства с владельцем; plumbing smoke этого не доказывает.

## 21. Основные риски

### Недостаточная скорость self-play

Меры: маленькая сеть, batching, несколько CPU actors, ограниченное MCTS,
профилирование, curriculum и возможный переход критических частей на C++/Rust
только после измерения узких мест.

### RL не стартует из-за редкой награды

Меры: простые terminal-rich окончания, постепенное увеличение материала,
исторические соперники и контроль распределения ничьих.

### Катастрофическое забывание стиля

Меры: персональный replay, отдельный style prior, ограничение KL или смешанный
loss, регулярные style-метрики.

### Переобучение на human-feedback

Меры: высокий loss weight при ограниченной доле batch, версионирование,
validation и возможность отката к предыдущему snapshot.

### Утечка test

Меры: неизменяемый test manifest, запрет включения новых feedback-партий в test,
отдельные команды evaluation и явное логирование обращений к test.

### Потеря долгого run

Меры: атомарные snapshots, два последних сохранения, graceful stop, checksums и
проверка resume на коротких тестовых run до длительного обучения.

## 22. Утверждённые решения перед кодом

Перед началом реализации зафиксированы:

1. **Утверждено:** Python 3.12, `uv`, локальная `.venv`, `pyproject.toml`,
   `uv.lock` и `src`-layout.
2. **Утверждено:** PyTorch как основной framework; MPS для обучения и inference
   на Mac, CPU fallback для тестов, CUDA как будущий переносимый backend. MLX
   рассматривается только после профилирования рабочей модели.
3. **Утверждено:** вход `board119-v1` формы `[batch, 119, 8, 8]` с
   абсолютной ориентацией, восемью состояниями истории, признаками повторения,
   стороной хода, рокировками, halfmove clock и en passant.
4. **Утверждено:** `az73-v1` с 73 пространственными плоскостями, индексом
   `plane * 64 + from_square`, абсолютными направлениями и color-relative
   underpromotion; нелегальные действия маскируются до softmax.
5. **Утверждено:** игровой export `chessy-model-v1` в Safetensors с JSON
   manifest и checksums; полный `chessy-snapshot-v1` как атомарная директория
   с весами, PyTorch training state, run/data/replay/league manifests и
   проверкой совместимости.
6. **Утверждено:** исходный YAML `chessy-config-v1`, строгая Pydantic
   validation, canonical resolved JSON, run ID из времени, имени и fingerprint;
   неизменяемый `resume` и явный `fork` для изменения эксперимента.
7. **Утверждено:** локальный FastAPI + WebSocket backend и
   React/TypeScript/Vite frontend с `react-chessboard`; backend владеет правилами
   и MCTS, собранный UI раздаётся одной Python-командой только на `127.0.0.1`
   с автоматическим выбором свободного порта.
8. **Утверждено:** `mcts-puct-v1`, `c_puct=1.5`, Dirichlet noise
   `alpha=0.3`/`epsilon=0.25` только для self-play; curriculum использует
   64/96/128 симуляций, игра по умолчанию — 128, MPS batch — до 32 позиций,
   resignation выключен до отдельной калибровки.

Все восемь решений утверждены. Первым кодовым этапом становится каркас проекта,
после чего реализуется шахматное кодирование и его тесты,
поскольку от него зависят датасет, сеть, MCTS, интерфейс и совместимость всех
будущих чекпоинтов.
